# 原理：这套微软离线语音为什么能在 macOS 上跑

## 一句话

Android 版用的语音包是**微软 Windows/嵌入式平台的标准 Embedded Speech 语音包**，模型文件和密钥都没有变，
只是换了一个运行时：从 APK 里的 Android `.so` 换成微软官方在 NuGet 上发布的 **macOS dylib**。
JNI 那一层（Android 专属）本来就是薄薄一层包装，macOS 上直接用 C++ API 调同一套逻辑。

所以这不是「逆向重写 TTS」，而是「把同一个模型接到官方跨平台运行时上」。
唯一需要额外解决的是：语音包里的模型是加密的，需要那把 license 钥匙。

## 1. 语音包是什么

`multitts-instance/app/src/main/assets/msvoice/<voice>/` 里是一个完整的语音包（9 个，约 385MB）：

| 文件 | 作用 |
|---|---|
| `Tokens.xml` | 语音注册信息（语音名、CLSID、语种、性别、版本） |
| `am_v5_encoder.bin` / `am_v5_decoder.bin` | 声学模型（acoustic model，编码器/解码器） |
| `device_vocoder_v6_streaming.bin`（Aria 是 v5） | 声码器，把声学特征还原成波形 |
| `MSTTSLoc<Lang>.dat`、`<Lang>.name/message/address.dat` | 语言资源（发音词典、文本正则等） |
| `<Lang>.TextAnalyzer.dat` | 文本分析（分词、TN） |
| `2052.INI` / `MSTTSLocZhCN.ini` | 文本规范化（TN）、词界配置 |
| `phones.txt` / `punc.txt` | 音素表、标点表 |
| `AppxManifest.xml` / `AppxBlockMap.xml` / `AppxSignature.p7x` | Windows Appx 打包残留，运行时不用 |

这些不是 MultiTTS 自己做的格式，就是微软 Embedded Speech 的 voice 包原样（Windows 上放在
`C:\Program Files\...\Speech_Models\TTS\` 也是这一堆文件）。

## 2. 模型是加密的

`am_v5_encoder.bin` 开头：

```
00000000: 5a00 0000 7960 2f34 541c 3134 2729 1245  Z...y`/4T.14').E
```

- 不是 ONNX（ONNX 开头是 `08 xx` 的 protobuf），也不是 zip；
- 头部 `5a 00 00 00` = 90，后面 90 字节是头，再往后是密文；
- 不同语音包的头前 ~90 字节大部分相同，正文完全不同 → 典型的「头部 + 加密正文」。

**解密钥匙就是 `license`**。用官方 macOS 运行时、空 license 去合成，报错很明确：

```
TTS error code = EMBEDDED_TTS_ERROR_WRONG_DECRYPTION_KEY.
Invalid embedded speech synthesis model key.
```

也就是说：模型不是「校验 license」，而是**用 license 派生的密钥解密模型**。
没有正确的钥匙，一个字节都解不出来。

## 3. 钥匙从哪来

Android 版的代码里：

```kotlin
cfg.setSpeechSynthesisVoice(voice.displayName, MsVoices.licenseFor(voice))
// licenseFor: raw.startsWith("Key:") ? raw : "Key:$raw"
```

- `zh-TW-YunJheNeural` 用的是语音包 `config.yaml` 里自带的 inline key（明文，直接能用）；
- 其余 8 个走「设备 license」：`SpeexBridge.getLicense(0)`，实现在 `libspeexdsp.so` 里。

先排除「运行时被魔改」的可能：把 APK 里的 `libMicrosoft.CognitiveServices.Speech.extension.embedded.tts*.so`
和 NuGet 官方 1.45.0 的安卓包对比，**md5 完全一致**。说明 MultiTTS 没有 patch 解密逻辑，
它拿到的就是货真价实的 license —— 只是藏在了 native 库里。

`getLicense` 本身是控制流平坦化 + MBA（mixed boolean-arithmetic）混淆的字符串还原，
函数体 ~5KB ARM64，硬读很痛苦。但这些字符串是**纯计算出来的常量**（不依赖设备信息），
所以最省事的办法是让它自己算：用 Unicorn 把这段 ARM64 代码跑起来，
在它调用 JNI `NewStringUTF` 的那一刻把结果截下来。

`tools/extract_license.py` 就是这个思路（可以用 `arm64-v8a/libspeexdsp.so` 复现）：

```bash
python3 -m pip install unicorn pyelftools
python3 tools/extract_license.py ../multitts-instance/app/src/main/jniLibs/arm64-v8a/libspeexdsp.so 0
# → ZCjZ7nHDSLvf4gpELteM4AnzaWUjTpn7UkV7D@vvksl0w1SNgon6d1905WANbktDc9S39oaA4r29HJNayXvTq8fJsq
```

实现要点：

1. 解析 ELF 的 `PT_LOAD` 段映射进 Unicorn，`.bss` 清零；
2. 处理 `.rela.dyn/.rela.plt`：本 .so 自己导出的符号（`_lxy_oxor_any_1X/Y`）指回真实地址，
   外部 libc 符号指向桩函数（malloc/memcpy/strlen/pthread/time… 用 Python 实现）；
3. 造一个假的 `JNIEnv`（`env->functions` 指向一张函数表，每项都指到桩）；
4. 调 `getLicense(env, clazz, 0)`，桩捕获 `NewStringUTF(env, str)` 的 `str`，停止模拟。

三个 `type` 的结果：

| type | 内容 |
|---|---|
| 0 | 96 字符的 license 密钥（就是我们要的） |
| 1 / 2 | 微软的模型授权声明文本（reference number 2774316 / 2881039），即语音包里的 EULA |

这 8 个语音共用同一把设备 license；`zh-TW-YunJheNeural` 必须用它自己的 inline key（换用设备 key 会
同样报 `WRONG_DECRYPTION_KEY`）。这些常量都写在 `src/voices.cpp` 里，也可以用环境变量覆盖：

```bash
MSTTS_LICENSE='Key:...' ./build/mstts say "test"          # 全局覆盖
MSTTS_LICENSE_ZH_CN_XIAOXIAONEURAL='Key:...' ./build/mstts say "test"  # 单语音覆盖
```

## 4. macOS 运行时从哪来

微软把 Embedded Speech 的扩展库作为独立 NuGet 包发布（C++/C#/Java 通用）：

| NuGet 包 | 内容 |
|---|---|
| `Microsoft.CognitiveServices.Speech` | `Speech.core.dylib`（主库）+ C++ 头文件 |
| `...Extension.Embedded.TTS` | `...extension.embedded.tts.dylib`（离线 TTS 扩展，**内含 TTS 引擎**） |
| `...Extension.ONNX.Runtime` | `...extension.onnxruntime.dylib`（onnxruntime，跑模型用） |

每个包都带 `runtimes/osx-arm64/native/` 和 `runtimes/osx-x64/native/`。
`scripts/fetch-sdk.sh` 会把两套 dylib `lipo -create` 成 universal 二进制，放进
`third_party/ms-speech/lib/`，加起来 71MB。

版本组合上有个坑：`Embedded.TTS 1.53.0` 的 nuspec 声明依赖 `ONNX.Runtime 1.53.0`，
但 nuget 上 **没有** 1.53.0 的 ONNX.Runtime（最高 1.52.0）。实测 1.53.0 + 1.52.0 完全正常，
`fetch-sdk.sh` 就按这个组合拉。

链接的 3 个 dylib 都有 `@rpath` 安装名，工程里把可执行文件的 rpath 设成
`@executable_path/lib`，`make` 时把 dylib 复制到 `build/lib/`，所以 build 目录直接可跑。

## 5. 调用链和 Android 版一模一样

```
EmbeddedSpeechConfig::FromPath(<voiceDir>)
  → SetSpeechSynthesisOutputFormat(Raw24Khz16BitMonoPcm)
  → SetSpeechSynthesisVoice(displayName, license)     // 这里解密模型
  → SpeechSynthesizer::FromConfig(cfg, nullptr)
  → SpeakSsml(<speak><voice><prosody>...</prosody></voice></speak>)
  → AudioDataStream::FromResult(result).ReadData()     // 24kHz/16bit/mono PCM
```

`displayName` 必须逐字用语音包 `Tokens.xml` 里的 Name，例如
`Microsoft Xiaoxiao (Natural) - Chinese (Simplified, China)`。

SSML 里 `prosody` 的 rate/pitch 用百分比，实测 `'20%'` 和 `'+20%'` 等价（都加速 20%），
`'-20%'` 减速，`pitch` 不影响时长，所以和 Android 版 `SsmlBuilder` 的写法可以直接复用。

## 5.1 采样率：24kHz 是离线引擎的硬上限

网上关于 Azure 语音「支持 48kHz」的说法针对的是**在线**接口（以及 `Audio48Khz*Mp3` 这类编码格式）；
离线 Embedded 引擎只出 PCM，而且采样率由模型锁死。实测（`make probe-formats`）：

| 请求 | 结果 |
|---|---|
| `Raw24Khz16BitMonoPcm` / `Riff24Khz16BitMonoPcm` | ✓ 正常，24k/16bit/mono |
| `Raw48Khz16BitMonoPcm` / `Riff48Khz16BitMonoPcm` | ✗ `Request sample rate (48000) is not supported, supported sample rate is 24000` |
| `Raw44100Hz16BitMonoPcm` / `Riff44100Hz16BitMonoPcm` | ✗ 同上（44100） |
| `Raw22050Hz16BitMonoPcm` / `Raw16Khz*` / `Raw8Khz*` | ✗ 同上（22050/16000/8000） |
| 所有 Mp3 / Opus / Silk / Siren / AMR / G722 | ✗ `Only PCM format is supported` |

dylib 里有一个内部属性 `SPEECH-SynthOfflineIgnoreFormatCheckAndResampling`，设成 `true`
后 48k/44.1k 确实不再报错，但返回的字节数和 24k 请求**一模一样**（61200 B），也就是只跳过了
格式检查、并没有真的重采样；照着 48k 去播会变成两倍速。所以不能用它来“解锁高采样率”。

另外 dylib 里的 `inputSampleRate must be 16000` / `outputSampleRate must be 24000 or 48000`
是内部重采样器的约束（离线 runtime 的 16k 输出 → 24k/48k），只对某些内部路径生效，
对 `AudioDataStream` 拿到的成品没有影响。

结论：语音包和 vocoder 就是 24k 的，44.1k/48k 只能自己上采样，属于插值，不会增加信息量。
工程里把格式收敛成 `Engine::kSampleRate/kChannels/kBitsPerSample` 三个常量（只出现一次），
WAV 编码器、HTTP 头、播放器都按传入的采样率工作，单测覆盖 24k/44.1k/48k 的 WAV 头，
以后真要接 48k 音源也不用改这一层。

## 6. 实测数据（本机，Apple Silicon / macOS 15.7）

| 语音 | 文本 | 音频时长 | 合成耗时 |
|---|---|---|---|
| 晓晓 | 春眠不觉晓…（24 字） | 4.90s | 189 ms（首次，含加载模型） |
| 晓晓 | 同一句再合成 | 4.90s | 90 ms |
| 云希 | 同上 | 4.90s | 93 ms |
| 云哲 | 同上（繁体） | 5.06s | 94 ms |
| Aria | The quick brown fox…（44 字符） | 2.79s | 110 ms |
| 晓晓 | 1928 个汉字（80 句） | 392.0s | 7.3 s（≈53× 实时） |

`doctor` 里 9 个语音单句耗时 52–148ms。模型加载是懒加载，每次 `SpeechSynthesizer` 新建
都会重新读模型（约 50–100ms），所以没有做常驻缓存 —— 对个人使用足够快，也避免几百 MB 常驻内存。

## 7. 为什么没走 sherpa-onnx / 开源模型

开源方案（sherpa-onnx + VITS / Piper / Kokoro）当然能跑，但：

- 音色和 Android 上听到的不是同一批（晓晓/云希这些是微软的私有模型，开源界没有等价物）；
- 中文韵律和文本正则要另外配（开源模型对数字、英文混读的处理差异明显）；
- 这个工程的诉求是「把已有的这套搬到 macOS」，复用原模型是唯一能做到 100% 一致的路。

外部的 ONNX 方案仍然保留为备选：`sherpa-onnx` 的 macOS 版很好装，
如果要加，在 `Engine` 里加一个后端即可（CLI 层面就是多一个 `--engine`）。

## 8. 还没做的

- GUI（现在只有 CLI + 本地 HTTP 服务；`http://127.0.0.1:8765/` 有个试听页）。
- 44.1k/48k 输出（引擎只给 24k，见 5.1；要就自己重采样，且不会提升音质）。
- 并行合成（SDK 全局状态，目前串行；53× 实时暂时够用）。
- 语音包管理（增删语音：把目录放进 `<voices>/<code>/`，并在 `src/voices.cpp` 里登记）。
